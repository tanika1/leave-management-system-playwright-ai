# FRAMEWORK_ARCHITECTURE.md

This document defines the automation framework architecture for the Leave Management System and serves as the implementation blueprint for all future automation work. It builds on the authoritative project context: PROJECT_DISCOVERY.md, AGENT.md, MEMORY.md, RISK_MATRIX.md, and TEST_STRATEGY.md. It does not repeat those documents; it specifies how we will engineer the automation to realize the strategy within a 5‑hour hackathon while preserving long‑term maintainability.

=========================================================
OVERALL AUTOMATION ARCHITECTURE
=========================================================

- Goals
  - Support API, UI, and E2E automation with Playwright + TypeScript.
  - Maximize stability and maintainability using clear layering, fixtures, and reusable helpers.
  - Prioritize API‑first tests for highest ROI; add minimal, high‑value UI/E2E per TEST_STRATEGY.md.
  - Keep design pragmatic: simple, predictable, easy to extend by new contributors.

- High‑level Layers
  - Tests (api/ui/e2e/smoke/regression) → Fixtures (context, api client, date factory) → Abstractions (Page Objects, Component Objects, API Client) → Shared (models, constants, utils) → Config (env, reporters, artifacts).

- Key Design Decisions
  - Composition over inheritance for Page/Component Objects and API client utilities.
  - Tests hold assertions and oracles; Page/Component Objects hold navigation and interaction only.
  - API client is thin, typed, and side‑effect free; response validation helpers live in utils.
  - Deterministic locators (getByRole/Label/ARIA) to reduce flakiness.

=========================================================
FOLDER STRUCTURE & RATIONALE
=========================================================

Root folders (under project automation root):

- docs/
  - Architecture and usage: this file, TEST_STRATEGY.md references, contributor notes.

- config/
  - playwright.config.ts template, env config loaders, reporter settings.

- constants/
  - Endpoint paths (/api/...), roles, leave types, statuses, tags, timeouts.

- models/
  - TypeScript interfaces/types for request/response payloads (LeaveRequestRecord, LeaveTypeBalance, etc.).

- utils/
  - Cross‑cutting helpers: date range factory (weekday ranges), response validators, expect helpers, logger.

- fixtures/
  - Playwright fixtures for apiClient, dateFactory, testData, and configured test context (baseURL, storageState if applicable).

- api/
  - API client modules: strongly‑typed functions for each endpoint group (employee, manager, health/shell).

- pages/
  - Page Objects: AppShellPage, EmployeeViewPage, ManagerViewPage, Sidebar.

- components/
  - Component Objects: BalanceTable, RequestsTable, RejectInlineWidget.

- tests/
  - Subfolders by layer/purpose: api/, ui/, e2e/, smoke/, regression/, exploratory/.

- hooks/
  - Global setup/teardown hooks (start/stop app optional), per‑project hooks if needed.

- testdata/
  - Static seeds for scenarios if any; dynamic factories generate most dates.

- types/
  - Global type declarations (custom matchers, test types augmentations).

- reports/
  - HTML/JUnit reports generated by the runner.

- artifacts/
  - Traces, screenshots, videos on failure.

=========================================================
DEPENDENCY FLOW & LAYERED ARCHITECTURE
=========================================================

Textual dependency map:
- tests → fixtures → (pages | components | api) → (models | constants | utils)
- pages → components (composition)
- api → (models | constants | utils)
- fixtures → config/constants/utils

Rules:
- Test files depend downward only; no lateral coupling.
- Page Objects never depend on test code or API client.
- API client has no dependency on Page Objects.
- Utils and constants are leaf layers (no upward dependency).

=========================================================
EXECUTION FLOW
=========================================================

- Playwright Test Runner orchestrates projects (api/ui/e2e) with shared config.
- Per‑test fixtures provision apiClient, dateFactory, and (for UI/E2E) a configured page/context.
- Tests create preconditions using API (e.g., submit request) before UI visualization steps.
- On failure, capture trace/screenshot/video per policy.
- Reports are generated at run end (HTML + JUnit optional for CI).

=========================================================
CONFIGURATION STRATEGY
=========================================================

- playwright.config.ts (in config/)
  - baseURL: http://localhost:5173
  - use: { trace: 'retain-on-failure', screenshot: 'only-on-failure', video: 'off' }
  - projects: api (use request context), ui (headed=false), e2e (headed=false, retries=1)
  - retries: default 0 (api), 1 (ui/e2e)
  - reporter: [['html', { outputFolder: 'reports/html' }], ['junit', { outputFile: 'reports/junit/results.xml' }]]
  - workers: api → auto; ui/e2e → limited (e.g., 2–4) to reduce shared‑state collisions

- Environment
  - API base: derive from baseURL or explicit env (VITE_API_BASE_URL / proxy). For API client, set base to `${process.env.API_BASE ?? 'http://localhost:5000'}`.
  - Config loader reads .env or CLI args; do not hardcode in test code.

=========================================================
ENVIRONMENT STRATEGY
=========================================================

- Default local dev: frontend http://localhost:5173, backend http://localhost:5000 via Vite proxy.
- Allow overriding API base via environment variable for future staging.
- Validate health endpoint before suites; skip gracefully if unavailable (clear message to user).

=========================================================
FIXTURE STRATEGY
=========================================================

- Global Fixtures
  - apiClient: Initialized Playwright APIRequestContext with baseURL to backend.
  - dateFactory: Helpers for generating weekday ranges and UTC boundary dates.
  - testData: In‑memory registry of created IDs per test for log clarity (not for teardown).
  - page/context: Standard Playwright fixtures with sensible timeouts and event logging.

- Scope
  - apiClient/dateFactory/testData: per‑test scope to ensure independence.
  - Optional globalSetup: health check to fail fast if services aren’t running.

=========================================================
PAGE OBJECT STRATEGY
=========================================================

- Responsibilities
  - Encapsulate navigation and user interactions only.
  - Expose high‑level actions: switchRole, selectEmployee, submitLeaveForm, approveRequest, openRejectInline, confirmReject, cancelRequest.
  - Provide element getters using semantic locators (getByRole, getByLabel, aria‑label attributes from App.jsx).

- Non‑Responsibilities (do NOT place in POs)
  - Assertions or business oracles (keep in tests).
  - API calls or data assertions on responses.
  - Test data creation logic (lives in fixtures/api client).

- Proposed Page Objects
  - AppShellPage (sidebar, nav, role switcher, employee selector)
  - EmployeeViewPage (form + requests table)
  - ManagerViewPage (team requests table + approve/reject interactions)

=========================================================
COMPONENT OBJECT STRATEGY
=========================================================

- Use for reusable UI parts within pages:
  - BalanceTable (read values for assertions in tests)
  - RequestsTable (query rows by ID/status/type)
  - RejectInlineWidget (reason input + confirm/cancel)
- Keep components small and composable; no cross‑page logic.

=========================================================
API LAYER ARCHITECTURE
=========================================================

- Structure api/
  - health.ts: GET /api/health, /api/shell
  - employees.ts: GET /api/employees
  - employee.ts: balance, list, submit, cancel
  - manager.ts: list, approve, reject

- Patterns
  - Functions return { status, json } with typed json based on models/.
  - Validation helpers in utils/ (assertStatus, assertSchema minimal checks).
  - No internal retries by default; leave retries to test runner if needed.

=========================================================
SHARED UTILITY LAYER
=========================================================

- dateUtils: nextWeekday(startOffsetDays), rangeWeekdays(start, days), weekendOnlyRange(), utcBoundaryCases().
- expectUtils: custom tiny wrappers for readable diagnostics (e.g., expectStatus(response, 409, 'NotPending')).
- schemaUtils: minimal shape checks for presence of critical fields.
- logUtils: structured console logs gated by verbosity env.

=========================================================
TEST DATA STRATEGY
=========================================================

- Prefer generated date ranges to keep tests independent and deterministic.
- Use API to set up preconditions (submit) before approval/rejection/cancellation.
- No teardown necessary due to in‑memory state; rely on test isolation and unique IDs.
- Optional: restart backend between groups if needed (out of scope for 5 hours unless required).

=========================================================
CONSTANTS & CONFIG ORGANIZATION
=========================================================

- constants/endpoints.ts: strings for all endpoints.
- constants/enums.ts: roles, leave types, statuses.
- constants/tags.ts: smoke, api, ui, e2e, p1, p2.
- constants/timeouts.ts: default timeouts (short and sensible).

=========================================================
LOGGING STRATEGY
=========================================================

- Keep runtime logs minimal and useful: request method/path/status; key IDs; failure reasons.
- Enable verbose logs via env flag when debugging.

=========================================================
REPORTING STRATEGY
=========================================================

- Built‑in HTML reporter for local runs (reports/html).
- JUnit XML for CI (reports/junit/results.xml).
- Attach artifacts (traces/screenshots) to failing tests for judge review.

=========================================================
SCREENSHOT, VIDEO & TRACE STRATEGY
=========================================================

- trace: 'retain-on-failure' (UI/E2E only).
- screenshot: 'only-on-failure'.
- video: off by default to save time/space; enable selectively if needed.
- API tests: traces off (not useful), rely on request/response logs.

=========================================================
ERROR HANDLING STRATEGY
=========================================================

- Fail fast on status mismatches with diagnostic messages.
- Wrap critical actions with clear error messages; avoid generic assertions.
- Use expect.poll sparingly to await visible UI state post‑action instead of hard waits.

=========================================================
RETRY STRATEGY
=========================================================

- Global retries: 0 for API, 1 for UI/E2E.
- No per‑step retry loops; allow Playwright’s built‑in auto‑waiting and retries.
- Revisit if a specific UI flake is proven.

=========================================================
PARALLEL EXECUTION STRATEGY
=========================================================

- API tests: full parallel.
- UI/E2E: limited workers (2–4) to reduce contention on in‑memory backend.
- Tag‑based filtering: run @smoke subset first for quick validation.
- Support sharding for CI (PW_TEST_WORKER_INDEX based splitting).

=========================================================
CI/CD READINESS
=========================================================

- Node 20 setup → npm ci → npx playwright install --with-deps → run tagged suites.
- Upload reports/html and artifacts/ as build artifacts.
- Gate merges on smoke passing; full regression optional due to time.

=========================================================
SCALABILITY CONSIDERATIONS
=========================================================

- Tagging strategy allows selective runs as suite grows.
- Centralized selectors and endpoints reduce maintenance cost.
- Adding auth/persistence in future: extend fixtures and config without touching tests.

=========================================================
PLAYWRIGHT DESIGN STANDARDS
=========================================================

- Locator Strategy
  - Prefer getByRole, getByLabel, getByTestId (if available) over text/xpath.
  - Use ARIA labels present in App.jsx (e.g., aria‑label on tables/buttons).
  - Centralize selectors in Page/Component Objects; no raw selectors in tests.

- Assertions
  - Tests own assertions; POs expose data/handles.
  - Combine status code + message assertions for API.
  - Avoid brittle text matches; prefer role/label + semantic fields.

- Page Object Responsibilities
  - Navigation and interactions only; return data needed for assertions.
  - No waits beyond Playwright’s auto‑waiting unless specific condition requires expect(locator).toBeVisible().

- Fixture Responsibilities
  - Provide configured apiClient, dateFactory, and page/context.
  - Avoid embedding business assertions; fixtures set up state.

- API Client Responsibilities
  - Typed request/response methods; no test assertions inside.
  - Include minimal status check utilities or return raw response + parsed json.

- Utility Classes
  - Pure functions; no side effects; small and composable.

- Custom Matchers (Optional)
  - A thin set (e.g., toHaveHttpStatus) if it improves clarity; otherwise rely on expect with helpers.

- Reusable Helpers
  - createPendingRequest(employeeId, type, range)
  - approveRequest(id)
  - rejectRequest(id, reason)
  - cancelRequest(id, employeeId)

- What NOT to place in Page Objects
  - Assertions, API logic, global state, cross‑test coordination.

=========================================================
TEST ORGANIZATION
=========================================================

- Smoke: Minimal, fast checks across P1 APIs and one E2E happy path.
- Regression: Broader coverage of P1/P2 per RISK_MATRIX.md.
- API: Validation matrices, state transitions, status semantics, boundary cases.
- UI: Role/employee switching, error feedback visibility, essential navigation.
- End‑to‑End: Submit→Approve, Submit→Reject, Submit→Cancel (highest business value).
- Exploratory: Charters executed manually with notes stored under docs/ or tests/exploratory/notes.md.
- Critical Business Flows: Tagged @critical for prioritized execution.
- High‑Risk Scenarios: Tagged @p1, @p2 for quick targeting.

=========================================================
NAMING CONVENTIONS
=========================================================

- Files: kebab-case (submit-approve.e2e.spec.ts), folders lower-kebab.
- Classes (PO/Components): PascalCase (EmployeeViewPage, BalanceTable).
- Methods: camelCase (submitLeave, approveRequest).
- Variables: camelCase; constants UPPER_SNAKE_CASE.
- Fixtures: camelCase (apiClient, dateFactory).
- Tests: suffix .spec.ts; locate under tests/<layer>/.
- Page Objects: pages/<Feature>Page.ts; Components: components/<Name>.ts.
- Utilities: utils/<domain>-utils.ts; Models: models/<name>.ts.

=========================================================
CODING STANDARDS
=========================================================

- Async/Await
  - Always await async Playwright calls; no floating promises.

- Locator Usage
  - No xpath unless unavoidable; prefer role/label/testid.

- Error Handling
  - Descriptive assertion messages; fail fast on unexpected statuses.

- Assertions
  - Specific and meaningful; avoid asserting multiple unrelated things in one test.

- Comments & Logging
  - Keep comments concise and value‑adding; use logger for important context only.

- Reusability
  - Centralize selectors and endpoints; extract helper functions when duplicated.

- Code Reviews
  - Enforce quality gates; small PRs; require trace on failure before approval.

=========================================================
QUALITY GATES
=========================================================

- No hard waits (page.waitForTimeout) — use auto‑wait or expect conditions.
- No raw selectors in tests; use POs/components.
- No duplicated locators; selectors live in one place.
- Semantic locators first (role/label/testid); no xpath unless justified.
- Independent tests; no shared state dependence.
- Reusable actions via helpers/POs; minimal duplication.
- Assertions must reflect business oracles from TEST_STRATEGY.md.
- Clean, commit‑ready code; passes lint (if enabled) and runs locally.

=========================================================
IMPLEMENTATION ROADMAP
=========================================================

- Phase 1 — Framework Foundation
  - Setup Playwright config, folder skeleton, reports/artifacts dirs.
  - Outputs: config baseline, empty scaffolds for folders, README for contributors.

- Phase 2 — Core Infrastructure
  - Implement constants, date utils, basic logger, health check.
  - Outputs: constants/, utils/, minimal fixtures.

- Phase 3 — API Layer
  - Build api/ modules (health, employees, employee, manager) with models/ types.
  - Outputs: typed clients + response helpers.

- Phase 4 — Page Objects
  - Implement AppShellPage, EmployeeViewPage, ManagerViewPage with semantic locators.
  - Outputs: pages/ and components/ with small composable objects.

- Phase 5 — UI Tests
  - Add small smoke checks for role/employee switching and error feedback mapping.
  - Outputs: tests/ui/smoke specs tagged @smoke.

- Phase 6 — API Tests
  - Implement P1 matrices (submit, approve, cancel, reject, balance, weekday counting, status semantics).
  - Outputs: tests/api/ with tags @p1, @regression.

- Phase 7 — E2E Tests
  - Implement the three critical workflows per TEST_STRATEGY.md.
  - Outputs: tests/e2e/ @critical set with traces on failure.

- Phase 8 — Reporting & Documentation
  - Ensure reporters configured; add CI example; document run commands and tags.
  - Outputs: reports, docs updates, contribution guidelines.

Dependencies: Each phase builds on previous; API layer before E2E; POs before UI tests.

=========================================================
SELF REVIEW
=========================================================

- Principal SDET View: Clear separation of concerns; small, composable objects; deterministic API focus for ROI.
- Playwright Maintainer View: Uses built‑in fixtures/reporters; avoids over‑customization; favors role/label locators.
- Engineering Manager View: Achievable within hackathon; scalable tagging; simple onboarding.
- Hackathon Judge View: Strategy maps to risks; artifacts and evidence are first‑class; avoids boilerplate bloat.

Eliminations:
- No custom runner or heavy reporting plugins.
- No complex DI container or inheritance hierarchies.
- No data layer mocks (real API used for truth).

This architecture balances simplicity with rigor, is immediately implementable, and aligns with the project’s risk‑based, API‑first test strategy.
